## What it does
- `publishWorkOrder(order, workOrder, repoDir)`: when `ghConfig().enabled` is true and the
  work order verdict is PASS, creates branch `fleet/<order>/<wo>`, commits ONLY `workOrder.owns`,
  pushes (no force), and opens a DRAFT PR (title = work order title, body = REPORT.md text +
  verdict line) via the GH-1 `openDraftPr`. Repo from `FLEET_GITHUB_REPO` (owner/name), token
  from `GITHUB_TOKEN`. Returns `{prUrl?, branch, dryRun}` or `{skipped: reason}`; never throws.
- `ciVerdict(order, workOrder, checks?)`: `"RED"` if any check failed, `"GREEN"` if all passed,
  else `"PENDING"`. No PR, dry-run, or no token => `"PENDING"`. `checks` is an optional test seam.
- `applyCiDowngrade(order, workOrder, checks?)`: downgrades a PASS to REDO exactly once on a RED
  verdict, naming the failed checks in the review text; idempotent via `ciDowngraded`.
- Default behaviour with `FLEET_GITHUB` unset is unchanged: `publishWorkOrder` returns
  `{skipped}` immediately, `publishPass` adds no trace step, and the tick block is skipped
  because no `prUrl` is ever set.

## Open issues
- Cosmetic only: the harness prints the check number twice (e.g. `PASS 1. 1. ...`) because the
  number is in both the record name and the print template. Left as-is so the single permitted
  run's output is reported verbatim; a follow-up may de-duplicate it.
- `publishWorkOrder` creates the branch with `git checkout -b` (falling back to `git checkout`)
  because GH-1 exports no branch-creating helper and `github.ts` was not to be edited. It never
  force-pushes and never switches to a protected branch for the commit (`commitOwned` still
  refuses main/master).
- `ciVerdict`/`applyCiDowngrade` honour an injected `checks` array before the dry-run guard, so
  the proof can exercise the RED path without a token; real calls still return `"PENDING"` in
  dry-run (proved by check 4).
- The `prUrl` summary line and the CI downgrade only appear when `FLEET_GITHUB=1` has actually
  produced a PR; with the feature off they cannot trigger.
