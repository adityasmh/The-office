# Work order: the worker token guard (CEO top priority: "not wasting a single token, no looping workers")

From: manager. Model: deepseek-flash (only; never deepseek-v4-pro). Repo: C:\Users\user\Desktop\Default Project (Windows PowerShell).
When the job is done, print the final report and END your turn; never wait, hold, loop, poll, re-read this order, or say Holding. Do not restart the router. Keep it small: two scripts, one check, one short doc.

## Why
Workers on the DeepSeek key repeatedly looped and burned prepaid credit (USD 4.02 -> 2.89 in under an hour). Measured from logs\jcode-*-20261002.log (each worker turn prints a line like `[Tokens] upload: 260289 download: 1065 cache_read: 259584 cache_write: 0`): the looping startup worker = 121 turns, 80x the word "Holding", 11.0M upload tokens; fallback-fix worker 128 turns / 20.2M; policy worker 61 turns / 15.7M. Loop signs seen: the assistant answers just `Holding.` or `Continue holding.` every turn, repeats the same sentence, re-reads its own order, or keeps working long after printing its final report. Only the manager's manual checks caught them. We need an automatic guard.

## Build
1. `ops/spawn-worker.ps1` (the ONLY way the manager spawns workers from now on). Params: `-Name` (letters, digits, dashes), `-Message` OR `-OrderFile` (if OrderFile: the message is "You are a jcode worker for the manager. Read and execute the work order in <file> exactly as written. When the job is done print the final report and END your turn; never wait, hold, loop, re-read your own order again, or say Holding."), `-MaxMinutes` (default 15), `-MaxUsd` (default 0.15). It HARD-REFUSES any model other than deepseek-flash: it always runs `jcode.exe run -p deepseek -m deepseek-flash -C <repo> "<message>"` (jcode path C:\Users\user\AppData\Local\jcode\bin\jcode.exe; hidden window via Start-Process with the message quoted as ONE argument; stdout/stderr to logs\jcode-<Name>-<yyyyMMdd>.log/.err.log), refuses if `-Model` contains "pro". It appends one JSON line {name,pid,log,startedAt,maxMinutes,maxUsd} to logs\workers.json (JSON lines file) and starts the guard (below) hidden if it is not already running (single-instance by pid file logs\worker-guard.pid, verify the pid is a live powershell running worker-guard.ps1). It prints the pid and nothing else.
2. `ops/worker-guard.ps1` (long-running, hidden, one instance): every 15 s, for every registered worker whose pid is alive (verify the process is jcode.exe with ' run ' in its command line; NEVER touch any other pid, terminals, router, supervisor, Laya, Kafka), read ONLY the bytes appended to its log since the last pass (track the file offset; never re-read the whole log; the file is locked for writing by the worker, open it with FileShare.ReadWrite) and update per-worker counters: turns, upload/download/cache_read/cache_write sums from the `[Tokens] ...` lines, and an ESTIMATED USD cost with PEAK DeepSeek flash prices (conservative): cache hit USD 0.014 per 1M, cache miss (upload minus cache_read, minimum 0) USD 0.44 per 1M, output (download) USD 1.32 per 1M. KILL the worker (Stop-Process -Id <pid> -Force, that pid only) and log the reason when ANY of: (a) the log text contains the word `Holding` 2 or more times in total; (b) the same trimmed assistant line (ignore lines starting with `[Tokens]`, `[todo]`, `[bash]`, `[edit]`, `[read]`, `->`, `→`, and empty lines) occurs 6+ times among the last 80 appended lines; (c) 90 seconds have passed since the first line matching `(?i)final report` while the worker is still alive (a finished worker must end by itself); (d) wall clock since start exceeds MaxMinutes; (e) estimated cost exceeds MaxUsd; (f) the log has not grown for 150 s while the worker is alive and at least 60 s old (hung). Append every kill and every 5 minutes a one-line status per live worker to logs\worker-guard.log (timestamp, name, pid, turns, est USD, reason or "ok"), and append a final line per finished or killed worker to logs\token-ledger.jsonl {date,name,turns,upload,download,cache_read,estUsd,endedBy}. The guard exits by itself after 30 minutes with no live registered worker (the spawn wrapper restarts it on demand). It must use almost no CPU (sleep 15 s between passes, no recursion over directories, no WMI in the loop: use Get-Process -Id and one CimInstance command-line check only when a pid is first seen).
3. `ops/worker-guard-check.ps1`: tests with temporary files and a harmless dummy process (e.g. `ping -n 600 127.0.0.1` registered as a fake worker, with a fake log you append to; a guard run in a mode `-Once` or `-TestRoot <dir>` so the test never touches real logs\workers.json): assert it KILLS the dummy on each of (a)-(f), does NOT kill a healthy worker that prints normal varied lines with plausible token lines, does NOT kill an unregistered process, and that spawn-worker.ps1 refuses a model containing "pro". Parser check (`[System.Management.Automation.Language.Parser]::ParseFile`) on all three scripts with 0 errors. Everything must pass.
4. Register the already running worker pid 21280 (log logs\jcode-no-maglev-20261002.log, started about 07:16, name no-maglev, MaxMinutes 12, MaxUsd 0.15) in logs\workers.json so the guard covers it, then start the guard through spawn-worker's guard-start logic (not a new jcode worker). Confirm with a line in logs\worker-guard.log.
5. `docs/WORKER_GUARD.md` (at most 25 lines): how to spawn (`ops\spawn-worker.ps1 -Name x -OrderFile docs\ORDER_x.md`), the six kill rules, where the logs/ledger are, and that fleet terminals (jcode TUI windows) are NOT covered (they are managed by the Fleet).
6. Append a timestamped entry to docs/AGENT_COORDINATION.md. Do not edit any other source file. No secrets printed, no deletes. Final report at most 8 lines (files, check results, guard pid, registered workers), then END.

## EDGE CASES (CEO: "consider all the edge cases and make the guard work that way"). Every item below must be handled in the code AND covered by a case in ops/worker-guard-check.ps1. Changes to the defaults above: MaxUsd default is 0.30 (a legitimate 128-turn code-fix worker re-reads ~20M cached tokens = about USD 0.28 at peak flash prices, so 0.15 would kill honest work); warn in the guard log at 70% of MaxUsd; MaxMinutes default 15.
A. What the logs really look like (read logs\jcode-startup-20261002.log, jcode-kafka-up-20261002.log and jcode-deepseek-fallback-20261002.log first, with Select-String, never Get-Content -Raw: they may be locked): the model's reasoning is written ONE TOKEN FRAGMENT PER LINE with a leading emoji marker (lines like `💭 Respond`, `💭 "`, `💭 H`, `💭 olding`), tool calls as `[bash] $ ...`, `[edit]`, `[todo]`, results as `→ ...`, and the visible assistant answer as plain lines (e.g. `Holding.`). So (1) loop detection must REASSEMBLE the fragments: strip the marker, join consecutive fragment lines into text, and search that text (phrases like `keep holding`, `continue holding`, `I'll hold`, `Respond "Holding`) as well as plain answer lines; a line-by-line repeat check on fragments would misfire (`💭 .` repeats everywhere legitimately). (2) Word rule: kill when the plain answer lines equal `Holding`/`Holding.`/`Continue holding.` (case-insensitive, trimmed) 2 or more times, OR the reassembled thought text matches those phrases 3+ times in the last 200 lines. The single word "Holding" inside a normal sentence (e.g. "holding the lock", a table cell) must NOT count by itself. (3) Repeated-line rule only on plain answer lines (not fragments, not bracket/arrow/token lines), 6+ identical in the last 80.
B. Reading: process only COMPLETE lines (up to the last newline, keep the partial remainder for the next pass); if the file is shorter than the stored offset (truncated/rotated) reset the offset and counters note; open with FileShare.ReadWrite; decode UTF-8 (emoji); tolerate a missing log (worker just started: wait up to 60 s) and tolerate malformed `[Tokens]` lines (skip, never crash).
C. Identity and safety: registry stores pid AND the process creation time; before any kill verify jcode.exe + ' run ' in the command line AND the creation time matches (a reused pid must never be killed); never kill the guard's own pid/parent, terminals (no ' run '), the router/supervisor/Laya/java/Kafka, or the manager session; kill ONLY the jcode pid, NOT its process tree (a worker may have started Kafka or other long-lived processes that must survive); after Stop-Process confirm the pid is gone (retry once) and log it.
D. Time: sleep/hibernate or a stalled guard makes pass gaps huge (last night the machine slept 10 hours): measure elapsed time as the SUM of pass deltas, each capped at 60 s (a gap bigger than 120 s counts as 15 s and is logged as "gap"), so waking up never triggers MaxMinutes or the idle rule falsely; use local time for the ledger date and handle midnight rollover; never use wall-clock subtraction alone.
E. Idle (hung) rule vs long tool calls: a worker legitimately waits minutes on a long command (download, test, tsc, kafka start) with no log output. Before applying rule (f) check whether the jcode pid has live child processes (one Get-CimInstance Win32_Process -Filter "ParentProcessId=<pid>" only when idle > 90 s): with children alive use a 420 s idle limit, without children 150 s. The 60 s startup grace applies.
F. Cost estimate edge cases: token lines missing or unparsable for a long time -> fall back to a log-size backstop (kill above 2 MB of log growth per worker unless the registry entry sets a bigger MaxLogMb); never divide by zero; cache_write counts as cache miss input; clamp negatives to 0. Estimated cost is an estimate: log it as such, and reconcile against the real balance in the ledger when available.
G. Money guards beyond one worker: (1) concurrency cap: spawn-worker refuses when 3 registered workers are alive; (2) duplicate cap: refuse a second live worker with the same -Name; (3) daily cap: sum of today's estUsd in logs\token-ledger.jsonl plus live workers; refuse a new spawn when it exceeds env WORKER_DAILY_USD_CAP (default 1.50); (4) balance floor: spawn-worker reads the DeepSeek credit from GET http://localhost:8787/company/budget/real (providers.deepseek.balanceUsd; 5 s timeout; if the router is down or the number is missing, do not block but log "balance unknown") and refuses below USD 1.00 unless -Force; the guard itself, when it can read the balance and it is below USD 0.30, kills ALL registered workers and logs it. Never print or log any key.
H. Process robustness: wrap every pass in try/catch so one bad log never stops the guard; log exceptions (message only); single instance via a NAMED MUTEX (not only the pid file) so two simultaneous spawn-worker calls cannot start two guards; the guard's own log logs\worker-guard.log is capped (when over 1 MB keep the last 500 lines); registry and ledger writes use UTF-8 WITHOUT BOM (use [System.IO.File]::AppendAllText with New-Object System.Text.UTF8Encoding($false); Windows PowerShell 5.1: no `??`, no ternary, no `-AsHashtable`); tolerate a half-written last registry line; the registry and ledger directories may not exist yet (create logs\ if needed).
I. Normal endings: when a registered pid exits by itself write the ledger line with endedBy "finished"; when the worker already printed its final report and exits within 90 s that is a normal ending, not a kill; a worker that finishes in under 10 s is fine; deleting/renaming a worker's log mid-run must not crash the guard.
J. Fleet terminals (jcode TUI windows, started by the Fleet with `-p ... -m ...` and NO ' run ') are NOT killed by this guard. Investigate read-only (5 minutes max) whether `C:\Users\user\.jcode\sessions\session_*.journal.jsonl` has per-turn usage fields; if it does cheaply, add a REPORT-ONLY section to the guard log (terminal name, estimated tokens in the last 10 minutes, flagged when a terminal produced more than 20 turns in 10 minutes with no file edits); if not cheap, just document the gap in docs/WORKER_GUARD.md. Never kill a terminal.
K. Tests (all in ops/worker-guard-check.ps1, with fake logs written to a temp folder and a dummy `ping -n 600 127.0.0.1` process as the fake worker; never touch the real registry/logs): each kill rule fires; fragmented-thought `Holding` loop fires; the word "holding" in a normal sentence does NOT; a healthy varied worker with plausible token lines is NOT killed; a partial last line is not parsed as complete; a truncated log resets without crashing; a wrong creation time (simulated pid reuse) is NOT killed; a registered pid that is not jcode is NOT killed; a simulated 10-hour pass gap does NOT trigger MaxMinutes or idle; a worker with a live child process is not killed by the idle rule before 420 s; missing token lines trigger only the log-size backstop; the concurrency, duplicate, daily-cap and balance-floor refusals each work; spawn-worker refuses a model containing "pro"; the guard survives an exception thrown by a bad registry line. Report the number of cases passed.
